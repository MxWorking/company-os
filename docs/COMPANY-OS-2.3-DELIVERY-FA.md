# Company OS 2.3 | ثبت‌نام، تأیید عضویت و درخواست‌های مالی

وضعیت: **نسخه آزمایشی قابل بررسی (Review Candidate)** | ۲۰۲۶-۱۰-۱۲

## آنچه واقعاً پیاده‌سازی شد

### ۱. ثبت‌نام شخصی، تأیید مدیر و عنوان شغلی
- در صفحه ورود، دو عملکرد «ورود» و «ثبت‌نام» وجود دارد.
- عضو نام/نام خانوادگی، نام کاربری، رمز قوی (۱۲ کاراکتر یا بیشتر)، کد سازمان (`company-os` در نصب پیش‌فرض)، واحد و **عنوان شغلی پیشنهادی** را وارد می‌کند.
- سرور حساب را **غیرفعال** و درخواست را **Pending** ذخیره می‌کند؛ **Membership** و نقش سازمانی هنوز ایجاد نمی‌شود.
- مدیر در «حساب و دسترسی‌ها» فهرست درخواست‌ها، عنوان شغلی پیشنهادی و واحد را می‌بیند؛ می‌تواند عنوان را تصحیح، نقش تعیین و تأیید/رد کند.
- عنوان «حسابدار»، «مدیر» یا «مدیرعامل» که متقاضی خودش وارد کرده **هیچ مجوزی ایجاد نمی‌کند**.
- پس از تأیید، عضویت سازمانی اضافه، حساب فعال و ورود مجاز می‌شود.
- در صورت رد، درخواست‌کننده می‌تواند با رمز خودش عنوان را اصلاح کند و تقاضای مجدد بفرستد؛ حساب تا تأیید بعدی همچنان غیرفعال است.
- مدیر سازمان (`manager`) مجاز به بررسی ثبت‌نام کارمند/حسابدار است، ولی نمی‌تواند کسی را به `admin` یا `manager` ارتقا دهد. این اختیارات فقط برای `owner/admin` است.

### ۲. نقش‌ها و سایدبار بر اساس مجوز واقعی API
| نقش سیستمی | دسترسی پیش‌فرض |
|---|---|
| `owner/admin` | مدیریت کل سازمان، تأیید/رد عضویت و تخصیص نقش‌های حساس |
| `manager` | دسترسی به ماژول‌های کاری/مالی؛ داشبورد سازمانی محدود به Tenant؛ تأیید اعضای عادی و حسابدار؛ بدون حق اعطای نقش ارشد |
| `accountant` | حسابداری و اسناد مالی، همکاری تیمی، پیام‌های مالی، پشتیبانی؛ در پروژه‌ها فقط رکوردهای مجاز |
| `member` | وظایف مجاز، چت/همکاری، یادداشت‌ها، پشتیبانی و **درخواست مالی بدون دسترسی به دفتر مالی** |
| `viewer` | مشاهده محدود کارهای محول‌شده، یادداشت‌های شخصی، پشتیبانی و درخواست مالی شخصی |

- نقش پایه توسط مدیر تعیین می‌شود و می‌توان برای ماژول‌های غیرحساس مجوزهای فردی تعریف کرد.
- **دسترسی مالی به عضو عادی با Grant عمومی قابل بازکردن نیست**؛ ابتدا باید نقش حسابدار یا مدیریت مجاز به‌صورت صریح اعطا شود.
- فیلتر سایدبار فقط UX است؛ کنترل دسترسی واقعی در FastAPI و برای هر درخواست دوباره انجام می‌شود.
- کاربران مدیر و کارمند در دیتابیس موجود حفظ می‌شوند؛ جداول جدید افزوده می‌شوند و حساب مدیر قبلی تغییر رمز نمی‌کند.

### ۳. درخواست مالی از کارکنان به واحد حسابداری
- زیرگروه «مالی و حسابداری → درخواست‌های مالی» برای تمام اعضای واردشده قابل دسترسی است.
- ثبت موضوع و شرح درخواست پرداخت/هزینه/خرید؛ نمایش درخواست‌های خود برای اعضای عادی.
- حسابداران و مدیران می‌توانند صندوق درخواست‌های شرکت را ببینند، پاسخ بدهند و وضعیت درخواست را تغییر دهند (`open`, `in_review`, `answered`, `closed`).
- مکالمات هر درخواست با شناسه درخواست و شناسه سازمان/کاربر در دیتابیس ثبت می‌شود؛ دیگران درخواست را نمی‌بینند.
- **این فرایند به‌صورت REST و با تازه‌سازی دستی است، نه WebSocket بلادرنگ، نه ایجاد خودکار سند حسابداری.** تصمیم ثبت سند باید توسط حسابدار انجام شود.

## مسیرهای API جدید
| روش | مسیر | دسترسی |
|---|---|---|
| POST | `/api/v2/auth/register` | عمومی، ایجاد حساب غیرفعال |
| POST | `/api/v2/auth/reapply` | متقاضی ردشده با رمز معتبر |
| POST | `/api/v2/auth/application-status` | متقاضی با رمز معتبر، بدون ارسال رمز در Query String |
| GET | `/api/v2/membership-applications` | مدیر سازمان یا مدیر ارشد |
| POST | `/api/v2/membership-applications/{id}/review` | مدیر سازمان / مدیر ارشد با محدودیت ارتقای حساس |
| GET/POST | `/api/v2/finance-requests` | اعضای تأییدشده |
| GET/POST | `/api/v2/finance-requests/{id}/messages` | صاحب درخواست یا حسابدار/مدیر مجاز |
| PATCH | `/api/v2/finance-requests/{id}/status` | حسابدار/مدیر مجاز |

## راه‌اندازی و ارتقا از نسخه ۲.۲.۱
1. قبل از هر تغییر از PostgreSQL Volume و فایل `.env` یک نسخه پشتیبان **امن و خارج از مخزن** تهیه کنید. هیچ فرمان `docker compose down -v` اجرا نکنید.
2. کد نسخه جدید را در پوشه پروژه استخراج و فایل `.env` معتبر نسخه قبلی را در ریشه، کنار `docker-compose.yml` نگه دارید. مقادیر محرمانه را در Git/ZIP قرار ندهید.
3. در همان پوشه اجرا کنید:

```bash
docker compose up -d --build --force-recreate
docker compose logs --tail=100 backend
```

4. با حساب Owner قبلی وارد شوید، «حساب و دسترسی‌ها» را باز کنید و یک ثبت‌نام آزمایشی با نام کاربری جدید انجام دهید.
5. ثبت‌نام باید در فهرست درخواست‌های بررسی دیده شود. تا پیش از تأیید، ورود حساب جدید باید رد شود.
6. پس از تأیید به‌عنوان کارمند، بررسی کنید گزینه حسابداری مخفی باشد، درخواست مالی باز شود و API دفتر حسابداری خطای ۴۰۳ بدهد.
7. پس از تبدیل کاربر به حسابدار، دوباره ورود/تازه‌سازی کنید و مجوز مالی را آزمایش نمایید.

## آزمون‌ها و مرزهای اطمینان
- ۴۳ تست Python با وضعیت `passed` در حالت pytest جداگانه، شامل ایجاد درخواست عضویت، ورود ممنوع قبل از تأیید، رد، درخواست مجدد، کنترل سمت سرور حسابداری، درخواست‌های مالی خصوصی و جداسازی سازمان‌ها.
- بررسی نحوی TypeScript/TSX و CSS با ابزار محلی موفق بود.
- نصب پکیج‌های npm در این محیط تا ۳۰ ثانیه به نتیجه نرسید؛ بنابراین **Build واقعی Next.js، Docker Build، QA بصری و Penetration Test تأیید نشده‌اند**.
- جدول‌های جدید با `Base.metadata.create_all` ایجاد می‌شوند؛ برای Production باید Migrationهای بازبینی‌شده Alembic و طرح بازگشت/پشتیبان‌گیری آماده شود.
- ثبت‌نام عمومی هنوز **Rate Limit توزیع‌شده، CAPTCHA، تأیید مالکیت ایمیل/شماره همراه، جلوگیری از Abuse و اعلان خودکار مدیر** ندارد. قبل از انتشار اینترنتی لازم است.
- برای بارگذاری کارت ملی/شناسنامه، الزامات امنیتی و مقررات حفاظت اطلاعات نسخه ۲.۲ همچنان برقرار است. رمزنگاری تنها یکی از کنترل‌های مورد نیاز است.
- حسابداری حرفه‌ای، چت WebSocket، پیامک OTP و LLM واقعی هنوز محصول کامل Production-ready نیستند.
- **هیچ Push به GitHub و هیچ Deploy در Vercel انجام نشده است.**
